# RAG 最小闭环（`rag/`）

> W3（11-17~11-23）交付物。目标不是「又一个能聊天的问答 demo」，而是把 RAG 最容易翻车的三件事——**无答案硬编、版本冲突瞎选、低置信乱答**——用可验证的规则兜住，并用标注集量出判定层到底对不对。
> 面试展示的是**工程闭环和评测意识**，不是模型能力。

## 这个闭环做什么

复用 `eval/` 已建好的切块（185 块）和 BM25 检索基线，往上接四步：

```
查询 → ① 检索(top-5) → ② 引用回溯(块→文档/章/条+原文) → ③ 判定(有答案/无答案/冲突/低置信) → ④ 人工兜底
```

| 环节 | 实现 | 为什么这么做 |
|---|---|---|
| ① 检索 | 直接调 `eval/retrieval.py` 的 BM25 + 中文字符二元组，k=5 | 不重造；k=5 时跨文档召回优于 k=3（实测） |
| ② 引用回溯 | 命中块映射回 `doc / chapter / clause / 原文片段` | 「引用能回到原文」是 W3 硬要求 |
| ③ 判定 | `decide_signal()`：top1 分数分三段 + 多文档分差比判冲突 | 把「敢不敢说不知道」「口径冲不冲突」变成可测分支 |
| ④ 兜底 | 冲突 / 低置信一律 `needs_human=true` | 对应 JD「对数、人工复核和回退机制」，不自动下结论 |

**单一真相源**：判定逻辑只在 `pipeline.py::decide_signal()` 实现，`pipeline --demo`（演示）与 `closure_eval.py`（评测）共用，避免两处逻辑漂移。

**判定规则**（规则化，不调模型）：

| verdict | 触发条件 | 动作 |
|---|---|---|
| `no_answer` | top1 < `low`（10.0） | 明确拒答，不硬编 |
| `conflict` | top-k 命中≥2 份文档且分差比 < `margin`（0.10） | 标人工，说清各自适用条件，不替用户择一 |
| `low_confidence` | top1 落在 [low, high) = [10, 11) 灰区 | 标人工复核，不自动作答 |
| `answered` | top1 ≥ `high`（11.0）且未触发冲突 | 给引用；答案要点仍须人工回原文核对 |

阈值用 `eval/questions.csv` 30 题标注集网格校准（low 5–11 / high 10–16 / margin 0.1–0.5 / k=3–20），最优 k=5 下对齐率 76.7%。**是启发式校准值，样本小，换语料需重标**，不是固定真理。

## 真实结果（2026-11-18，非 mock）

判定层是否对齐题目预期行为：**76.7%**（23/30）。注意这是「判定行为命中率」，**不是答案正确率**。

| 类型 | 判对 |
|---|---|
| 有答案 18 | 16/18 |
| 无答案 6 | 3/6 |
| 跨文档 4 | 3/4 |
| 版本冲突 2 | 1/2 |

7 个判错样本及逐条归因见 `report.md`。失败集中在两处，都是词法检索的结构性短板：

1. **无答案题蹭高分**（Q21/Q23/Q24）：「绩效考核指标」「Oracle 还是 MySQL」这类词在条文里高频，top1 越过拒答阈值 → 需加相关性下限，光调阈值会误伤有答案题。
2. **有答案题误判冲突**（Q01/Q12）：相邻块来自另一文档且分差比过小 → margin 单靠分数分不出来，需查询意图判别或提高 margin 门槛（会牺牲真冲突召回，需权衡）。

这两条就是接下来上向量检索 / 查询改写的依据，不是拍脑袋换方案。
