# RAG 最小闭环（`rag/`）

> W3（11-17~11-23）交付物骨架。目标不是「又一个能聊天的问答 demo」，而是把 RAG 最容易翻车的三件事——**无答案硬编、版本冲突瞎选、低置信乱答**——用可验证的规则兜住。
> 面试展示的是**工程闭环和评测意识**，不是模型能力。

## 这个闭环做什么

复用 `eval/` 已建好的切块（185 块）和 BM25 检索基线，往上接四步：

```
查询 → ① 检索(top-k) → ② 引用回溯(块→文档/章/条+原文) → ③ 判定(有答案/无答案/冲突/低置信) → ④ 人工兜底
```

| 环节 | 实现 | 为什么这么做 |
|---|---|---|
| ① 检索 | 直接调 `eval/retrieval.py` 的 BM25 + 中文字符二元组 | 不重造；检索命中层已有 9 题 recall@3=6/9 的真实基线 |
| ② 引用回溯 | 命中块映射回 `doc / chapter / clause / 原文片段` | 「引用能回到原文」是 W3 硬要求；答不出处就标出处 |
| ③ 判定 | `decide()`：top1 分数分三段 + 多文档命中判冲突 | 把「敢不敢说不知道」「口径冲不冲突」变成可测的分支 |
| ④ 兜底 | 冲突 / 低置信一律 `needs_human=true` | 对应 JD「对数、人工复核和回退机制」，不自动下结论 |

**判定规则**（现阶段规则化，不调模型）：

| verdict | 触发条件 | 动作 |
|---|---|---|
| `no_answer` | top1 < `low`（默认 8.0） | 明确拒答，不硬编 |
| `answered` | top1 ≥ `high`（默认 13.0）且单一文档 | 给引用；答案要点仍须人工回原文核对 |
| `conflict` | 多份文档的块同时高分命中 | 标人工，说清各自适用条件，不替用户择一 |
| `low_confidence` | top1 落在 [low, high) 灰区 | 标人工复核，不自动作答 |

阈值来自实测分数分布（强相关题 top1 约 15~30，无关题约 4.5），是**启发式初值**；必须用 `eval/questions.csv` 的 30 题标注集校准，不能当固定真理。

## 怎么跑

```bash
PY=C:\Users\12821\.workbuddy\binaries\python\envs\default\Scripts\python.exe

PY rag/pipeline.py --demo                       # 四类判定各跑一条
PY rag/pipeline.py --ask "发生数据安全事件后应在多长时间内报告监管部门"
PY rag/pipeline.py --ask "公司年度团建预算定多少"     # 看无答案拒答
PY rag/pipeline.py --ask "..." --json            # 结构化输出，方便接评测
PY rag/pipeline.py --ask "..." --low 8 --high 13 -k 5
```

前置：`eval/chunks.jsonl` 需在本地（跑 `python eval/chunk.py` 生成；该文件在 `.gitignore`，不进公开仓库）。无 API key、不花钱、离线可跑。

## 当前边界（诚实，面试可如实说）

- `answer_points` 仍是 `TODO(W4)`：**只判定 + 给引用，不生成答案文本**。W4 接真模型时用引用块生成，不得脱离原文。
- 阈值未用 30 题全量标定，四类判定的准确率**没有真实数字**，不能写进简历当成果。
- 复用的是词法检索，跨文档/版本冲突类召回弱（见 `eval/README.md` 已知短板）；向量检索与查询改写未做。
- 无 FastAPI 接口层、无会话、无持久化，仅单条查询闭环。
